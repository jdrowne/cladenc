# CladeNC

CladeNC (recursive acronym for Clade Next Clade) is a cleanroom implementation of the [Huxley-Gödel Machine](https://arxiv.org/abs/2510.21614) for agentic coding harnesses. It works by directed evolution. A directed evolution starts from one harness, the primogenitor. Harnesses procreate, each making a changed copy of its own source code, and are benchmarked on every task of the benchmarks a person brings. A part of the tasks of each benchmark is held out: no harness that procreates reads about them. The holdout tasks are divided in two, the selection tasks and the corroboration tasks. Artificial selection chooses which harness procreates, and at the end names the best harness, both by the selection tasks alone. Every harness is scored on the corroboration tasks and nothing is chosen by them, so they say how far the best harness is ahead of the primogenitor on tasks that had no part in the choosing. At each procreation of a harness other than the primogenitor, `cladenc` also conducts an experiment to test whether a progenitor is better at procreating better harnesses than the primogenitor. To conduct the experiment, `cladenc` establishes a baseline by having the primogenitor create a harness from the same source code that the progenitor uses to procreate the progenitor's child. The harness the primogenitor creates from the source code of the progenitor is the singleton control group harness.

## `cladenc`

```text
cladenc \
  --help \
  --version
```

| Flag | Required | Description |
| --- | --- | --- |
| `--help` | Not Required | Print the sub-commands and the flags of `cladenc`. |
| `--version` | Not Required | Print the version of `cladenc`. |

`cladenc` does its work through a sub-command. Called with neither a sub-command nor a flag, it prints what `--help` prints, on standard error, and exits with status 2. The `.deb` package of a release installs the program at `/opt/cladenc/bin/cladenc` and nothing outside `/opt/cladenc`, so a person calls the program by that full path, or adds `/opt/cladenc/bin` to `PATH` and calls it as `cladenc`.

| Sub-command | Description |
| --- | --- |
| `cladenc report` | Prints the report of a directed evolution that has ended, without changing it. |
| `cladenc resume` | Continues a directed evolution that stopped before its end. |
| `cladenc start` | Starts a new directed evolution and prints the directory of its best harness. |
| `cladenc status` | Prints the state so far of a directed evolution that has not ended, without changing it. |

`--help` after a sub-command prints its flags, and the manual page of the sub-command says the rest. The package installs the manual pages under `/opt/cladenc/share/man`: `man -M /opt/cladenc/share/man cladenc-start` shows the page of `cladenc start`, and `man cladenc-start` shows it where `/opt/cladenc/bin` is on `PATH`.

### `cladenc report`

```text
cladenc report \
  --json \
  --outputs-dir <DIR>
```

| Flag | Required | Description |
| --- | --- | --- |
| `--json` | Not Required | Print one JSON object in place of the table. |
| `--outputs-dir <DIR>` | Required | The outputs directory of the directed evolution to report on. |

`cladenc report` is for a directed evolution that has ended. It reads the journal in the outputs directory and prints the report of the directed evolution on standard output, without changing it: the model, how many procreations were started, the best harness, how many of the selection tasks, of the corroboration tasks and of the non-holdout tasks at least one harness completed, and for each harness its progenitor, whether it was created, which reads `unchanged` where its procreation left the copy of the source code as it was, how many of the selection tasks it completed and did not complete, how many of the corroboration tasks it completed and did not complete, how many of the non-holdout tasks it completed and did not complete, the counts of the selection tasks for its clade, which is the harness and all its descendants together, and how many seconds the harness ran in all its attempts together and how many its progenitor ran in the procreation that made it. Nothing is chosen by the corroboration tasks, so the counts of the corroboration tasks are where a person reads how far the best harness is ahead of the primogenitor. For the best harness against the primogenitor, `cladenc report` also prints how many corroboration tasks only the best harness completed, how many only the primogenitor completed, and how likely luck alone gives a lead at least as large where the two harnesses are equally good. Of the experiments that test whether a progenitor is better at procreating better harnesses than the primogenitor, `cladenc report` prints how many were conducted, in how many the progenitor's child was created, in how many the singleton control group harness was created, and in how many both were. Over the experiments where both were created, it prints how many corroboration tasks only the progenitor's child completed, how many only the singleton control group harness completed, and how likely luck alone gives a lead at least as large where the two are created equally well, counted as it is for the best harness against the primogenitor. Where no experiment created both the progenitor's child and the singleton control group harness, it says so in place of those counts and of the likelihood, and `--json` gives no likelihood for the experiments. A singleton control group harness has a row of its own in the table: the row names no progenitor, since the singleton control group harness is nobody's child, and names under `experiment` the progenitor's child of its experiment. The singleton control group harnesses are counted in no clade, and are left out of the count of the tasks at least one harness completed. Given a directed evolution that has not ended, `cladenc report` prints nothing on standard output: it says on standard error that the directed evolution has not ended and that `cladenc status` is the sub-command to call, and exits with status 2.

### `cladenc resume`

```text
cladenc resume \
  --outputs-dir <DIR>
```

| Flag | Required | Description |
| --- | --- | --- |
| `--outputs-dir <DIR>` | Required | The outputs directory of the directed evolution to continue. |

`cladenc resume` continues a directed evolution that stopped before its end, with the values that `cladenc start` was given, and prints the directory of the best harness on standard output once the directed evolution has ended, and nothing else there. It says on standard error what it is doing, and when the directed evolution ends it prints there what `cladenc report` prints, as `cladenc start` does. It is stopped in the way `cladenc start` is, and then prints no report. Of a directed evolution that had ended already, it prints the directory of the best harness and the report again and does nothing else.

1. It removes the containers that the directed evolution left running.
2. It builds the environment of every task again, as `cladenc start` does, from the copy of the task in the outputs directory and under the name the environment was given when the directed evolution was started. The image that the Dockerfile of each task starts from has to be on the machine: Docker fetches one that is not, from the registry of its name. A task whose environment is not built stops `cladenc resume` with exit status 2. It reads the `task.toml` of the copy of each task again, with the variables it names as they are set where `cladenc resume` runs. For a task whose `task.toml` names an image it builds nothing, and a task whose image is not on the machine, or which names a variable that is not set, stops `cladenc resume` with exit status 2.
3. It starts again each procreation, each creation of a singleton control group harness and each attempt that was under way when the directed evolution stopped.
4. It carries the directed evolution on to its end, as `cladenc start` does.

### `cladenc start`

```text
cladenc start \
  --benchmark <DIR> \
  --corroboration-tasks-percentage <NUMBER> \
  --harness-build-command <COMMAND> \
  --harness-run-command <COMMAND> \
  --max-concurrent-containers <COUNT> \
  --max-procreations <COUNT> \
  --max-task-health-check-retries <COUNT> \
  --max-verifier-health-check-retries <COUNT> \
  --model <NAME> \
  --model-key-file <FILE> \
  --model-url <URL> \
  --outputs-dir <DIR> \
  --primogenitor <DIR> \
  --procreation-docker-image <IMAGE> \
  --procreation-docker-image-build-timeout <SECONDS> \
  --procreation-dockerfile <FILE> \
  --procreation-timeout <SECONDS> \
  --selection-tasks-percentage <NUMBER>
```

| Flag | Required | Description |
| --- | --- | --- |
| `--benchmark <DIR>` | Required | The directory of a benchmark, which holds a directory for each task. The directory of a task holds its task specification in a file named `instruction.md`, [Harbor's task configuration](https://docs.harborframework.com/tasks/configuration) in a file named `task.toml`, its verifier in an executable file named `test.sh` in a directory named `tests`, and the Dockerfile of its environment in a directory named `environment`, as in [Harbor's task layout](https://docs.harborframework.com/tasks/verifier). `cladenc` obeys what the `task.toml` says of the environment of the task: its image, its working directory, its users, its variables and its health check. It keeps with each attempt the paths that the `task.toml` lists under `artifacts`. Where the `task.toml` says that the verifier of the task runs separately, `cladenc` runs the verifier in a container of its own, and a task whose verifier is in the image of that container needs no `test.sh`. A task whose `task.toml` names an image needs no Dockerfile. A task that holds no `task.toml` is refused, and so is one whose `task.toml` is not valid as Harbor's task configuration: `cladenc` checks every setting that Harbor's documentation names, those it does not obey among them. A task whose `task.toml` cannot be obeyed is refused, as is one that asks for what `cladenc` has no way to give: several steps, a GPU or a TPU, Windows, MCP servers, a skills directory, a path or a command of a container other than that of the harness, or the whole container of the harness in a verifier container. A task whose `environment` directory holds a Compose file, such as `docker-compose.yaml`, is refused, since an environment of more than one container cannot be built. So is a task whose verifier runs separately and whose `tests` directory holds a Compose file. A task's `solution` directory is never given to a container. The flag is given once for each benchmark of the directed evolution. `cladenc` fetches no benchmark: the tasks are read from the directory and copied into the outputs directory. |
| `--corroboration-tasks-percentage <NUMBER>` | Required | The percentage of the tasks of each benchmark that are corroboration tasks, a number above 0 and below 100, such as 15 or 12.5. `cladenc` scores every harness on the corroboration tasks and chooses nothing by them. The corroboration tasks and the selection tasks together are the holdout tasks, the tasks that no harness reads about when it procreates. `cladenc` draws them at random out of each benchmark: the number of its tasks times the percentage, divided by 100 and rounded to the nearest whole number, a half rounded up. It refuses a value that leaves a benchmark no corroboration task. |
| `--harness-build-command <COMMAND>` | Not Required | The shell command that builds a harness in a container, where one has to be built. |
| `--harness-run-command <COMMAND>` | Required | The shell command that runs a harness in a container. |
| `--max-concurrent-containers <COUNT>` | Required | The most containers running at once. |
| `--max-procreations <COUNT>` | Required | The most procreations to start, 1 or more. A procreation is one harness making another, and it counts once it is started, whether or not it creates its child. The container a singleton control group harness is created in is no procreation and is not counted. |
| `--max-task-health-check-retries <COUNT>` | Required | The most times the container of a task is brought up again, where its health check does not pass, 0 or more. It counts for a task whose `task.toml` gives a health check. Each retry is a new container, and `cladenc` waits before it: the `interval_sec` of the health check before the first retry, and twice as long before each retry after that. Where the health check passes in no container, the directed evolution stops and no result is recorded for the attempt. |
| `--max-verifier-health-check-retries <COUNT>` | Required | The most times a verifier container is brought up again, where its health check does not pass, 0 or more. It counts for a task whose verifier runs separately, in a container that the task's `task.toml` gives a health check. Each retry is a new container, and `cladenc` waits before it: the `interval_sec` of the health check before the first retry, and twice as long before each retry after that. Where the health check passes in no container, the directed evolution stops and no result is recorded for the attempt. |
| `--model <NAME>` | Required | The name of the model the harnesses call, as its server knows it. `cladenc` calls no model itself: it tells each harness the name, the address and the key. |
| `--model-key-file <FILE>` | Not Required | The file that holds the key the model is called with, on one line, and nothing else. It is given where the server of the model asks for a key. `cladenc resume` reads the file again. |
| `--model-url <URL>` | Required | The address the model is served at, by a provider or by a server of your own. In a container, `host.docker.internal` names the machine `cladenc` runs on. |
| `--outputs-dir <DIR>` | Required | The outputs directory, which `start` creates. |
| `--primogenitor <DIR>` | Required | The directory of source code that is copied to make the primogenitor, the harness the directed evolution starts from. |
| `--procreation-docker-image <IMAGE>` | Not Required | The Docker image every procreation, every build of a harness and every creation of a singleton control group harness is carried out in. No attempt is carried out in it: an attempt is carried out in the environment of its task, so a harness, once built, has to run in the environment of every task. Either this flag or `--procreation-dockerfile` is given, and not both. |
| `--procreation-docker-image-build-timeout <SECONDS>` | Not Required | The time limit of the build of that image. It is given with `--procreation-dockerfile`, and not without it. |
| `--procreation-dockerfile <FILE>` | Not Required | The Dockerfile that `cladenc` builds that image from, in place of `--procreation-docker-image`. |
| `--procreation-timeout <SECONDS>` | Required | The time limit of one procreation, which is one harness making another. |
| `--selection-tasks-percentage <NUMBER>` | Required | The percentage of the tasks of each benchmark that are selection tasks, a number above 0 and below 100, such as 45 or 12.5. `cladenc` chooses which harness procreates, and names the best harness, by the selection tasks alone. It draws them at random out of each benchmark, counted as for `--corroboration-tasks-percentage`, and the tasks that are neither selection tasks nor corroboration tasks are the non-holdout tasks. At 45 and 15, a benchmark of 500 tasks has 225 selection tasks, 75 corroboration tasks and 200 non-holdout tasks. `cladenc` refuses a value that leaves a benchmark no selection task, and two values that together leave a benchmark no non-holdout task, so a benchmark holds three tasks at the least. |

`cladenc start` starts a new directed evolution, carries it to its end, and prints the directory of the best harness on standard output, and nothing else there. It says on standard error what it is doing, and when the directed evolution ends it prints there what `cladenc report` prints: the table of the harnesses and the lines above the table, which say how far the best harness is ahead of the primogenitor on the corroboration tasks and how likely luck alone gives a lead at least as large. Ctrl-C, or one of the signals `SIGINT`, `SIGTERM`, `SIGQUIT` and `SIGHUP`, stops it sooner: it removes the containers it has running, prints no report and exits with status 1, and `cladenc resume` continues the directed evolution from there. A stop while the image or an environment is built comes before the directed evolution has a journal: `cladenc start` then exits with status 2, `cladenc resume` has nothing to continue, and the outputs directory is removed by hand before it is named to `cladenc start` again. While the directed evolution has not ended, `cladenc status` prints its state so far.

1. It draws the selection tasks and the corroboration tasks at random out of each benchmark: of the tasks of the benchmark, the percentage that `--selection-tasks-percentage` gives are selection tasks, the percentage that `--corroboration-tasks-percentage` gives are corroboration tasks, and the tasks that are left are the non-holdout tasks.
2. It creates the outputs directory, and copies into it the source code of the primogenitor and the tasks of each benchmark.
3. Where `--procreation-dockerfile` is given, it builds the image that every procreation and every build of a harness is carried out in.
4. It builds the environment of every task of every benchmark, before it brings up any container: an image built from the Dockerfile in the `environment` directory of the copy of the task, with that directory as the build context. The environments of one directed evolution share a name that `cladenc` draws at random, `cladenc-environments-` and sixteen hexadecimal digits, and each is tagged with the place of its task among the tasks, counted from 0, so that they are told apart from those of any other directed evolution on the machine. The image that the Dockerfile of a task starts from has to be on the machine: `cladenc` does not ask Docker to fetch it, and `docker build` has no flag that forbids it, so Docker fetches a base image that is not on the machine, from the registry of its name. The build of an environment has the time limit that the task's `task.toml` gives, as `build_timeout_sec` under `environment`, or 600 seconds where it gives none. What Docker printed is kept in `environments` in the outputs directory, and a task whose environment is not built stops the directed evolution with exit status 2. `cladenc` removes the environments it built once `cladenc start` or `cladenc resume` ends, whether the directed evolution finished, stopped or could not go on, so none is left on the machine. Where a task's `task.toml` says that its verifier runs separately and the task's `tests` directory holds a Dockerfile, `cladenc` builds the verifier image with the environments, from that Dockerfile with the `tests` directory as the build context and under the name of the environment of the task with `-verifier` after it, keeps what Docker printed in `verifier` beside what it printed for the environment of the task, and removes the image with the environments. An image that the `task.toml` names for the verifier, as `docker_image` under `verifier.environment`, has to be on the machine, as an image that it names for the environment of the task has to be. A task whose `task.toml` names an image, as `docker_image` under `environment`, has that image as its environment: `cladenc` builds nothing for the task, and the task needs no `environment` directory. The image has to be on the machine, since `cladenc` fetches no image, and a task whose image is not on the machine stops the directed evolution with exit status 2.
5. Where `--harness-build-command` is given, it builds the primogenitor.
6. It benchmarks the primogenitor. For each task of each benchmark, held out or not, the harness works on the task in a container of the environment of the task, in the working directory and as the user that the task's Dockerfile names, with its source code copied in at `/var/opt/cladenc/harness`. A harness, once built, has to run there, and the environment of every task has to hold `sh`, `sleep`, `rm`, `mkdir`, `chown` and `ln`. What the harness leaves in the working directory is kept with the attempt, with a list of every path it added, changed or removed in the container. Once the harness has ended, the task's `tests` directory is copied into the same container, where `/tests` is a symbolic link to the copy, at `/var/opt/cladenc/harbor/tests`, and the verifier, `/tests/test.sh`, writes its score in `/logs/verifier/reward.txt`, or one score for each label in `/logs/verifier/reward.json`. The harness completed the task where every score is 1, and what the verifier leaves in `/logs/verifier` is kept with the attempt. Where the task holds a `task.toml`, `cladenc` obeys what it says in place of what the image of the environment names: `workdir` under `environment` is the working directory of the harness and of the verifier, `user` under `agent` is the user the harness runs as, and `user` under `verifier` is the user the verifier runs as, each user a name or a number. The variables under `env` under `environment` are given to the container, so to the harness and the verifier alike, and those under `env` under `verifier` to the verifier alone. In the value of a variable, `${NAME}` stands for the value that the variable `NAME` has where `cladenc` runs, and `${NAME:-TEXT}` for that value, or for `TEXT` where `NAME` is not set there. A task that names a variable that is not set, and gives no text in its place, is refused. `cladenc` keeps the value of every variable of a task off every command line and out of the journal. The harness has the time limit that the task's `task.toml` gives, as `timeout_sec` under `agent`, and no time limit where it gives none. A harness that runs past its time limit is stopped, with every process it left running, and what it left is judged all the same. The verifier has a time limit of its own, `timeout_sec` under `verifier`, or 600 seconds where the task gives none, counted from the moment the harness ended or was stopped. No flag gives a time limit of an attempt. Where the task's `task.toml` gives a health check, as `command` under `environment.healthcheck`, `cladenc` runs that command in the container before it copies the harness in, and runs it again after each failure, as the settings beside the command say. The harness is started once the command has exited with status 0. Where the health check does not pass, the harness was never started, so `cladenc` does not record that the harness did not complete the task: it removes the container, waits, brings up a new container of the task and runs the health check there again, as many times as `--max-task-health-check-retries` gives. It waits the `interval_sec` of the health check before the first retry, or 5 seconds where the task gives none, and twice as long before each retry after that, and says each retry on standard error. Where the health check passes in no container, the directed evolution stops with exit status 1 and no result is recorded for the attempt: `cladenc` names the harness, the task, the number of tries and the directory that holds what the health check printed the last time it ran, and `cladenc resume` carries out the attempt again. Where the task's `task.toml` lists paths under `artifacts`, `cladenc` keeps each with the attempt as the harness left it, before the verifier is run: at the place the entry gives as `destination`, or at the path itself without its leading `/`, and, of a directory, without what the patterns the entry lists as `exclude` match. A path that is not in the container keeps nothing, and the attempt goes on. What a harness left in `/logs/artifacts` is kept as `artifacts/logs/artifacts`, though the task lists no such path. Before the harness is started, `cladenc` makes `/logs` a symbolic link to `/var/log/cladenc/harbor` and makes `/logs/artifacts` an empty directory that belongs to the user the harness runs as, so a harness that does not run as root saves a file there as well. Where the image of the environment already holds something at `/logs`, `cladenc` makes no link, leaves what is there, and makes `/logs/artifacts` inside it. `/logs` and `/tests` are the two names that Harbor's task layout fixes at the top of the filesystem, and `cladenc` makes no directory there: each of the two is a symbolic link, as the Filesystem Hierarchy Standard asks of an application. Where the task's `task.toml` lists commands under `verifier.collect`, which Harbor calls collection hooks, `cladenc` runs each in the container once the harness has ended or was stopped, before it keeps any path, with the time limit that the entry gives as `timeout_sec`, or 60 seconds where it gives none. A command that fails does not end the attempt, and what each command printed is kept in `collection-hooks`. Where the task's `task.toml` says that its verifier runs separately, with `environment_mode` under `verifier` written as `separate` or with a table named `environment` under `verifier`, `cladenc` removes the container of the harness once the paths are kept, and runs the verifier in a container of its own. That container is of the image that `docker_image` under `verifier.environment` names, or of the image built from the Dockerfile in the task's `tests` directory, each of which holds the verifier at `/tests/test.sh`, or else of the environment of the task as it is before a harness works in it, with the task's `tests` directory copied in. The verifier container follows the settings under `verifier.environment`, each as `cladenc` obeys it under `environment`, or those under `environment` where the task gives no such table. Where those settings give a health check, `cladenc` runs it in the verifier container, and nothing else is done there until it has passed. Where it does not pass, no verifier has judged what the harness left, so `cladenc` does not record that the harness did not complete the task: it removes the container, waits, brings up a new verifier container and runs the health check there again, as many times as `--max-verifier-health-check-retries` gives. It waits the `interval_sec` of the health check before the first retry, or 5 seconds where the task gives none, and twice as long before each retry after that, and says each retry on standard error. Where the health check passes in no container, the directed evolution stops with exit status 1 and no result is recorded for the attempt: `cladenc` names the harness, the task, the number of tries and the directory that holds what the health check printed the last time it ran, and `cladenc resume` carries out the attempt again. Each path that was kept is copied to the same path in the verifier container, so the verifier finds nothing else of what the harness left. No file that is copied in keeps a setuid or a setgid bit, and a symbolic link that points outside the path it was kept with is left out, as is a file that is not a regular file, a directory or a symbolic link. The container of an attempt is given no more CPUs and no more memory than the task's `task.toml` asks for, as `cpus` and `memory_mb` under `environment`, and a task that asks for more of either than Docker has stops the directed evolution with exit status 2.
7. It starts as many procreations as `--max-procreations` gives, each only once every harness created so far has been benchmarked in full, so that it chooses each harness that procreates with what every created harness completed in hand. In each, a harness reads its attempts at the non-holdout tasks, and what was kept of the harnesses it descends from and of the children it made before, and makes a changed copy of its own source code, its child. In the container of a procreation, the source code of the harness that procreates is at `/var/opt/cladenc/harness`, and the copy that the harness changes is at `/var/opt/cladenc/work`, the working directory. A procreation in which the harness leaves the copy of its own source code as it was creates no child, and is recorded as unchanged. Each child that is created is benchmarked as the primogenitor was. `cladenc start` chooses which harness procreates among those that have been benchmarked in full, partly by chance, and more often one that completed, together with its descendants, a larger share of the selection tasks they attempted. A harness whose procreation does not create its child is left out of the choice for the next procreation, whichever harness procreates in it. Each time a procreation of the same harness again does not create its child, the harness is left out for twice as many procreations as the time before: 2, then 4, then 8. Once a procreation of the harness creates its child, the harness is left out no longer, and the count starts again at 1. When every created harness is left out, `cladenc start` chooses among the harnesses that are left out for the fewest procreations still to come.
8. At each procreation of a harness other than the primogenitor, it conducts an experiment to test whether a progenitor is better at procreating better harnesses than the primogenitor. To conduct the experiment, it establishes a baseline: it brings up one more container, in which the primogenitor creates a harness from the same source code that the progenitor uses to procreate the progenitor's child. The source code that runs in the container is a copy of the source code of the primogenitor, and the source code that is changed is a second copy of the source code of the progenitor. What is there to read is what the progenitor is given in its procreation: the attempts of the progenitor at the non-holdout tasks, and what was kept of the harnesses the progenitor descends from and of the children the progenitor procreated before. The harness the primogenitor creates from the source code of the progenitor is the singleton control group harness. Where the primogenitor leaves the second copy of the source code of the progenitor as it was, no singleton control group harness is created. It is built and benchmarked in full, as the progenitor's child is, and it takes no other part in the directed evolution: it is never chosen to procreate, it is counted in no clade, it is not named the best harness, and the container it is created in does not count toward `--max-procreations`. Where the primogenitor procreates, no experiment is conducted: the progenitor's child and the singleton control group harness would be created in the same way. No flag leaves the experiment out. Each experiment has one more harness created and benchmarked in full, so a directed evolution can bring up about twice the containers, and take about twice as long, as its procreations and the attempts of the primogenitor and the children alone would.
9. It names the best harness: the created harness that completed the most selection tasks, a singleton control group harness left aside.
10. It prints on standard error what `cladenc report` prints, and on standard output the directory of the best harness.

### `cladenc status`

```text
cladenc status \
  --json \
  --outputs-dir <DIR>
```

| Flag | Required | Description |
| --- | --- | --- |
| `--json` | Not Required | Print one JSON object in place of the table. |
| `--outputs-dir <DIR>` | Required | The outputs directory of the directed evolution to print the state of. |

`cladenc status` is for a directed evolution that has not ended, whether the directed evolution is still going or stopped before its end. It reads the journal in the outputs directory and prints the state of the directed evolution so far on standard output, without changing it. It says first that the directed evolution has not ended, and then prints what `cladenc report` prints, with the harness that is ahead so far in place of the best harness. The harness that is ahead so far is the harness that would be named the best harness if the directed evolution ended now: the created harness, benchmarked in full, that completed the most selection tasks. For the harness that is ahead so far against the primogenitor, `cladenc status` prints how many corroboration tasks only the harness that is ahead so far completed, how many only the primogenitor completed, and how likely luck alone gives a lead at least as large where the two harnesses are equally good. What `cladenc status` prints is the state so far, which can change until the directed evolution ends: another harness can be ahead later, and a person who calls `cladenc status` many times reads many likelihoods, of which one is low by luck more often than one likelihood that is read once. Of the experiments, a corroboration task that the progenitor's child or the singleton control group harness has not attempted yet is left out. Given a directed evolution that has ended, `cladenc status` prints nothing on standard output: it says on standard error that the directed evolution has ended and that `cladenc report` is the sub-command to call, and exits with status 2.
