# cladenc takes a progenitor and a model

The user's design for `cladenc`: it does recursive self-improvement over coding harnesses after the HGM paper, and a person gives it two things to do so, a directory holding the source code of the progenitor harness and a model.

The directory holds the harness's source code, not the harness. The user corrected this on 2026-11-14, when an explanation of issue #28 said the directory held a harness. Say it that way in replies, issues and commits. The same day, still on #28, the user took the view that this calls for Docker: the source code is compiled in a container into a harness that can be run, where it compiles, and is run as it is where it does not. They put it as how things seem to them, not as a final decision.

Issue #28 was decided by the user on 2026-11-15: `cladenc run` gets two new options, one saying how a harness is built, given only where a harness has to be built, and one saying how a harness is run. I had put two heavier designs to them first, a launcher file or a `Dockerfile` required inside the source code, and an image plus a command; they found that overcomplicated and asked for plain options instead. The decision is written into #28's body and its `needs decision` label is removed. The user named the option that says how a harness is run, `--harness-run-command`, in place of the shorter name I had proposed. Mine, not the user's: the name `--harness-build-command`, made to match it, and when each command is run.

Also decided by the user on 2026-11-15: `cladenc` knows about Docker and is what starts the container a harness is built and run in, and Docker is a dependency of the `.deb` package. I had proposed that `cladenc` know nothing of Docker and leave it to the commands a person passes; the user turned that down. The image a container starts from is given in a third option, which the user named `--docker-image` in place of the name I had proposed. Last, the user decided that the source code of every offspring is kept, whether or not it builds, all in one folder, with `cladenc`'s own record saying which built; I had proposed deleting what does not build, and then a separate folder for it. With that, nothing in #28 is left to a person, and its `needs decision` label is off. Still mine and open to the session that does the work: when each command is run, that the source code sits on the machine and is mounted into the container, and that the keep-everything rule also covers an offspring whose making fails some other way. See [[the-simplest-design-is-offered-first]].

On 2026-11-15, while issue #27 was being brought up to date, the user said that the model can be a remote one or a self-hosted one and that `cladenc` is to support both. They gave Ollama as a way a self-hosted model can be served, as an example and not as a decision. The same day they decided the one thing #27 had left to a person: `cladenc` hands the model to the harnesses it starts and calls no model itself. I had recommended that, and told them its limit, that a search can only use a model whose server its harness can talk to. They then asked whether `cladenc` would ever have reason to call a model, so the question is not closed for good: work that calls for it would be an issue of its own. They also decided that a key reaches `cladenc` in a file that a flag names, per [[a-key-is-given-in-a-file]]. All of it is written into #27, and its `needs decision` label is off. The flags `--model` and `--model-url` were shown to the user by name and left as they were. Mine, not the user's, and written into #27 as proposals: the name `--model-key-file`, the variables `CLADENC_MODEL`, `CLADENC_MODEL_URL` and `CLADENC_MODEL_KEY` that a container is given, and starting each container so that it can reach a model served on the machine `cladenc` runs on. Do not design the model as a hosted provider's alone, or as a name alone: a self-hosted model also needs the address it is served at. The work of #27 landed later that day: `cladenc start` takes `--model`, `--model-url` and `--model-key-file` under the names proposed, hands a harness and the evaluator the three variables, and starts every container so that `host.docker.internal` names the machine. Two things in the code are mine and were not put to the user: every variable of a container, the key included, reaches Docker through the environment of the `docker` command and not on its command line, and `cladenc report` shows the model's name and address.

The user said this on 2026-11-14 while asking what issue #14 left to decide. They did not recognise a `cladenc` that starts programs its user writes, and the explanation of those programs confused them.

The code as it stood that day does not match. `cladenc run` takes no model and never runs a harness. It requires a procreator program and an evaluator program, a file of task ids and nine more options with no defaults, and does only the bookkeeping of the search. The plan of issues #1 to #9 says that `cladenc` never starts a harness and never calls a model. My own reading, not something the user said: that split was an earlier session's generalisation, not a thing the user asked for.

**Why:** The user wants a tool that is handed a harness and a model and improves the harness. Having to write the two programs that carry out the self-improvement leaves the main work to the person.

**How to apply:** Treat the two inputs as the intended interface. Do not describe the procreator and evaluator split to the user as settled, and do not deepen that contract, issue #14 included, before the mismatch is resolved with them. Open on 2026-11-14, and mine to ask, not things the user said: how `cladenc` starts a harness for a procreation and for an evaluation, where the tasks come from, what naming a model means, and whether the other options get defaults. Issue #27 first held the four. The user found that too much to be asked at once, so the same day it was split under [[one-indivisible-problem-per-issue]] into one decision to an issue, each labelled `needs decision`: #28 how a harness is started, #29 where the tasks come from, #27 what the model is, #30 whether the other options get defaults. #28 comes first, since #27 and #29 are blocked by it. My own reading, not something the user said: #28 and #29 state that `--procreator` and `--evaluator` are removed, not kept as a second way to carry out a job. #30 was decided by the user on 2026-11-15: no flag gets a default, the nine stay required, and the issue was closed as not planned, per [[no-flag-has-a-default]]. The two inputs are what a person brings to a search, not a count of flags. Related: [[the-paper-is-a-starting-point]], [[before-an-issue-is-labelled-needs-decision]], [[no-flag-has-a-default]].
