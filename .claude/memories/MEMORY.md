# Memory Index

- [Push to main](push-to-main.md) — commit/push directly to main, no feature branches or PRs; starting the autopilot counts as the ask, and so does asking for a change
- [Never quote the user verbatim](never-quote-the-user-verbatim.md) — restate what the user says in fresh words in memories, issues, commits, comments and summaries
- [A memory says what holds now](a-memory-says-what-holds-now.md) — a memory states the rule, its reason and how to apply it, and tells nothing of how the rule came about, who set it or what was done when
- [Room to be creative](room-to-be-creative.md) — creative work is wanted, not a narrow reading of the ask; no rule limits the work to only what was asked; an idea of the session's own is done in the work at hand, and the user is asked only for a decision of theirs
- [crates/ stores shared code](crates-stores-shared-code.md) — code more than one consumer uses is a package under crates/; here, code shared by the test tiers; a package under crates/ has tests of its own, in its own tests/ directory, held to full coverage of it, even one only tests use
- [The paper is a starting point](the-paper-is-a-starting-point.md) — keep the HGM paper's ideas, name things plainly and with biological words (directed evolution, artificial selection), and let cladenc leave the paper where a change improves it
- [The words about benchmarks](the-words-about-benchmarks.md) — taken from the industry's names but for non-holdout and corroboration: benchmark, task, task specification, workspace, grader, attempt, completed, result, to benchmark, score, and holdout, non-holdout, selection and corroboration tasks; defined in the README and `cladenc start --help`, never in a memory, and no file name given; a harness is benchmarked, never said to attempt every task; a new word is put to the user one at a time, in a reply
- [cladenc takes a primogenitor and a model](cladenc-takes-a-primogenitor-and-a-model.md) — a person brings the primogenitor's source code, a model and one or more benchmarks, and cladenc does the self-improvement itself, in Docker, calling no model itself
- [cladenc works offline and self-hosted](cladenc-works-offline-and-self-hosted.md) — no connection to the internet is needed, cladenc fetches nothing, and the person brings each thing a directed evolution uses, the whole benchmark among them
- [The work is clean-room](the-work-is-clean-room.md) — the paper is the only source; never read the authors' code, the Darwin Gödel Machine code, or a port or derivative of either
- [Every build is for Linux arm64](every-build-is-for-linux-arm64.md) — what CI compiles, tests, packages and releases is for Linux arm64 and no other platform
- [The only package is a .deb](the-only-package-is-a-deb.md) — no RPM is made, tested or released, and nothing in CI runs on Fedora
- [Repositories outside jdrowne stay out of the record](repositories-outside-jdrowne-stay-out-of-the-record.md) — not mentioned in a memory, and nothing from one quoted in anything public
- [Working without subagents](working-without-subagents.md) — no Agent or Workflow call, whatever the work's size; denied in the tracked settings.json, lifted only by the user's own ask
- [The work waits for CI](the-work-waits-for-ci.md) — while a run of the session's push is queued or in progress, do nothing else: no reading, editing, filing, committing or pushing; end the turn until the watch reports its end; what the user instructs is the exception, done in full at once; an autopilot reminder says so too
- [Only quick checks run before a push](only-quick-checks-run-before-a-push.md) — no test runs on the Mac: the unit, integration and end-to-end tests run in CI only; on the Mac only `cargo fmt --all` and `cargo check --all-targets`; clippy, coverage, linters, assert tools and the package are left to CI
- [Every run is watched](every-run-is-watched.md) — each run a push starts gets a background watch to its end, which exits with the run's status; runs are listed by the full hash `git rev-parse HEAD` prints, never a short one, and watched with the command the file gives; never take a run to have passed without reading it
- [CI runs the test binaries directly](ci-runs-the-test-binaries-directly.md) — release.yml runs each test binary by its path, not through cargo, so a test finds no variable cargo sets at run time, such as `CARGO_PKG_NAME`; a test that needs a variable from where it runs reads `PATH`
- [Long-running commands in the background](long-running-commands-in-the-background.md) — a command that can take more than about a minute is a background Bash call or a Monitor, with a time limit, never followed by a foreground wait
- [cargo is not on the shell's PATH](cargo-is-not-on-the-shell-path.md) — Rust is installed in ~/.cargo/bin; put it on PATH before calling cargo, and do not install it again
- [Several issues can be worked on together](several-issues-can-be-worked-on-together.md) — the autopilot takes the first unblocked issue it lists, an issue labelled `memories` or `autopilot` first outside `bylabel`, alone or with others it chooses; a blocked issue joins only with all its open blockers
- [Issues have no fixed form](issues-have-no-fixed-form.md) — no house layout and no section owed; write each issue in whatever form lets a session that never saw the conversation act on it
- [One indivisible problem per issue](one-indivisible-problem-per-issue.md) — an issue documenting more than one problem is split, re-using the issue as one of the splits; the problem alone sets an issue's size, never the amount of work or the context
- [An issue is brought up to date before work](an-issue-is-brought-up-to-date-before-work.md) — correct its title and body against the code as it stands before working on it, without adding work it does not ask for
- [A blocked_by edge states a real block](a-blocked-by-edge-states-a-real-block.md) — only where the waiting issue cannot be finished until the other closes; written with gh api and -F issue_id
- [Before an issue is labelled needs decision](before-an-issue-is-labelled-needs-decision.md) — check the memories and the code first, then write into its body what a person has to decide
- [Tests are written before code](tests-are-written-before-code.md) — the tests of a change come first and land in the same commit as its code; CI runs them, never the Mac
- [The checks the code faces](the-checks-the-code-faces.md) — written to pass release.yml: no comments, one assertion per test, no silencing directive, no linter config but etc/clippy/clippy.toml, Rust files up to 1000 lines, functions up to 50 statements, full coverage, rustfmt, and clippy's limits per function: complexity 15, nesting 4, 5 parameters, 200 lines; the release waits for every job that waits for none and is not a build
- [Each module of src is a directory](each-module-of-src-is-a-directory.md) — `src/<module>/mod.rs` for every module, a one-file module among them; `lib.rs` and `main.rs` are the only files directly in `src/`, and no file sits beside a directory of its name
- [The layout follows Rust's conventions](the-layout-follows-rust-conventions.md) — unit tests in a `tests/` directory beside each module's code, the other tiers under tests/, packages under crates/, nothing in Cargo.toml that Cargo finds itself; apart from Rust's conventions: mod.rs, no comments, linter settings under etc/
- [An item is as private as its uses allow](an-item-is-as-private-as-its-uses-allow.md) — in src/, no keyword, then `pub(super)`, then `pub(crate)`, and `pub` only for what src/main.rs or a tier under tests/ uses; a new item starts with no keyword
- [A tool is configured under etc](a-tool-is-configured-under-etc.md) — a tool's configuration file is under etc/ in a directory named for the tool, as etc/clippy/clippy.toml is, and the workflow points the tool at it; a linter gets one only for what it takes no other way
- [A commit closes at least one issue](a-commit-closes-at-least-one-issue.md) — one or more, a Closes #N line each; only a commit holding nothing but a failed run's fix or a change the user asks for directly closes none, and the fix writes Refs #N for each issue the failed commit closed
- [One commit per push](one-commit-per-push.md) — every push is exactly one commit, and that commit may hold several things at once: several issues' work, a failed run's fix, changes the user asked for, memory edits
- [A failed run is fixed before other work](a-failed-run-is-fixed-before-other-work.md) — when a run of the session's own push is found to have failed, the fix goes in the next commit pushed, with whatever else is finished, and no new work begins first
- [A push can leave its issues open](a-push-can-leave-its-issues-open.md) — after a push, read back each issue the commit closes and close by hand any still open
- [The first harness is the primogenitor](the-first-harness-is-the-primogenitor.md) — and a progenitor is the harness that procreates; the two are told apart, and parent is used for neither
- [A procreation has a progenitor, a copy and a child](a-procreation-has-a-progenitor-a-copy-and-a-child.md) — whatever is written about a procreation says which of the three harnesses it means; the copy is said as the progenitor's copy or the primogenitor's copy, never alone
- [A contradiction is the user's to settle](a-contradiction-is-the-users-to-settle.md) — where memories, a reminder, the skill or the code say opposite things about a rule or a design, the user picks which holds; put each to them on its own, as an issue or one per reply
- [What the user instructs is done](what-the-user-instructs-is-done.md) — in full and at once; no memory, reminder or wait for CI holds an instruction back, and it is never put back to the user as a decision
- [Issues about the session's rules are labelled](issues-about-the-sessions-rules-are-labelled.md) — `memories` on an issue about a memory, `autopilot` on one about an autopilot reminder or the skill
- [The singleton control group harness](the-singleton-control-group-harness.md) — `cladenc` conducts an experiment and establishes a baseline by having the primogenitor create the singleton control group harness from the progenitor's source code; never said as making a control
- [An issue says what is expected apart from what happens](an-issue-says-what-is-expected-apart-from-what-happens.md) — what is expected is written as expected, never as though it were so; the plain present is for what really happens
- [More tasks completed is not shown to be an improvement](more-tasks-completed-is-not-shown-to-be-an-improvement.md) — harnesses chosen by tasks their progenitors read about are expected to overfit, so nothing says as fact that they improve themselves; the holdout tasks are kept from the progenitors
- [A harness is not called a coding agent](a-harness-is-not-called-a-coding-agent.md) — say coding harness or agentic coding harness
- [The simplest design is offered first](the-simplest-design-is-offered-first.md) — lead a decision with the plainest choice, such as a command-line flag, explained in short concrete steps with every word defined
- [An explanation says what happens](an-explanation-says-what-happens.md) — for the user, define each of the project's words the first time, with an example in numbers, and say who does what in everyday words: which harness procreates, a harness completed a task; not the noun phrases of the issues and the code; name each thing again, with no this, that, these or those pointing back, call a thing what it is, never group A, and say the literal thing, never a figure of speech
- [The outputs directory](the-outputs-directory.md) — the name for the directory a directed evolution writes into, given with `--outputs-dir`; never called the run directory
- [A flag is not called an option](a-flag-is-not-called-an-option.md) — say flag for a `--name` argument; the README shows `cladenc` and each sub-command as a command block, then a table of its flags in alphabetical order, and under the table of a sub-command nothing but what it does
- [No flag has a default](no-flag-has-a-default.md) — every flag that takes a value is required and nothing about a directed evolution is assumed; a default is never proposed, and the count of required flags is not a problem; the seed is no flag, `cladenc` draws it
- [No flag for what cladenc already holds](no-flag-for-what-cladenc-already-holds.md) — a flag is for what only a person can tell `cladenc`; the source code of the primogenitor and of every harness is in the outputs directory, so no flag names it; a design inside one directed evolution comes before one that carries a harness between two
- [A key is given in a file](a-key-is-given-in-a-file.md) — a secret such as a model's key reaches cladenc in a file that a flag names, never as a flag's value or in an environment variable
- [Paths follow the Linux filesystem convention](paths-follow-the-linux-filesystem-convention.md) — nothing at the top of the filesystem, in a container or on the machine; what a container works with under /var/lib/cladenc, records under /var/log/cladenc
- [cladenc does not run jobs](cladenc-does-not-run-jobs.md) — say it brings up a container, for a procreation or for an attempt, and the code says action; it has no workers either, say the containers running at the same time
- [A sub-command does one job](a-sub-command-does-one-job.md) — the command line follows the Unix principle: one job, one directed evolution and one form of output for each sub-command; a comparison across directed evolutions is left to another program that reads `--json`
- [Every harness is benchmarked in full](every-harness-is-benchmarked-in-full.md) — each harness is benchmarked in full once it is made, and only then can procreate; a directed evolution is bounded by `--max-procreations`, not by a count of attempts
- [cladenc runs any benchmark](cladenc-runs-any-benchmark.md) — a benchmark is run as published and a free harness such as OpenCode is brought; a Harbor task's own configuration is obeyed in full and no flag overrides it; no harness, benchmark or converter is written in the repository, and example/ holds only a Dockerfile
- [An issue states a functional requirement](an-issue-states-a-functional-requirement.md) — a problem, or what cladenc is expected to do, seen from outside; never how to build it: no functions, files, Docker commands or mechanisms
- [A flag name says what it holds](a-flag-name-says-what-it-holds.md) — the kind of value in full and its use in front, such as `--procreation-docker-image`; never a bare word like image
- [CI caches all it can](ci-caches-all-it-can.md) — every job takes from the GitHub Actions cache what it would fetch or compile again: Rust builds, pip and npm downloads, the Docker images in `IMAGES`, what apt fetches; a new job gets the same
- [How long a directed evolution takes does not matter](how-long-a-directed-evolution-takes-does-not-matter.md) — run time on the Mac is never a reason for part of a benchmark, fewer procreations or a smaller model, nor a decision written into an issue
